# speech-english-tutor-webplugin

## 2. Overview
A specialized Chrome extension designed to assist English learners by providing real-time text-to-speech (TTS) and instant translations. It allows users to select text or images on any webpage to hear high-quality audio in English via OpenAI's TTS and see the corresponding Spanish translation in a draggable, interactive popup.

## 3. Architecture

- **Primary Pattern:** Chrome Extension Manifest V3 (MV3). This project utilizes a decentralized architecture comprising a Background Service Worker, Content Scripts, and an Offscreen Document to comply with modern browser security and persistence standards.
- **Structural Strategy:** Functional and Event-Driven asynchronous communication. The system relies heavily on the Chrome Messaging API to coordinate actions between different extension components.
- **Data Flow:** Unidirectional and mediated message passing. Content Scripts (UI) send requests to the Background Service Worker (Logic/API), which in turn communicates with the Offscreen Document (Media/Audio) and external OpenAI APIs. Feedback loops (e.g., audio progress) are routed back through the Service Worker to the active tab.
- **Key Concepts:** 
    - **Service Worker:** Acts as the central orchestrator, handling context menus, API authentication, and message routing.
    - **Offscreen Document:** A specialized context required by MV3 for continuous audio playback using the standard DOM `HTMLAudioElement` API, as service workers lack DOM access.
    - **OpenAI Integration:** Leverages GPT-4 Vision for image text extraction, GPT-4o-mini for translations, and specialized TTS models for natural-sounding speech.
    - **Draggable UI:** A custom-built, injected DOM element in the Content Script that provides a non-intrusive overlay for user interaction.
    - **Messaging Protocol:** Standardized message objects with a `type` property (e.g., `TTS_SPEAK`, `SHOW_TRANSLATION`) are used to trigger actions across different parts of the extension.
    - **Security:** API keys are managed in the Service Worker and injected via environment variables at build time. No sensitive information is exposed to content scripts.

## 5. Directory Map
*Key directories and their specific responsibilities in the system:*

- **src/**: The primary source directory containing all runtime logic and extension components. It houses the service worker, content scripts, and offscreen document logic.
- **src/background.js**: The extension's Service Worker and central orchestrator. It manages extension lifecycle events, context menu registration (`readSelectedText` for text and `translate-image` for images), and performs all secure OpenAI API interactions (TTS, Translation, and Vision).
- **src/content.js**: The UI layer injected into web pages. It is responsible for creating and manipulating the draggable translation popup in the DOM. It handles user interactions, manages local playback state (play/pause/seek), and listens for audio progress updates from the background.
- **src/offscreen.js**: Logic running within the specialized Offscreen Document. It handles the `HTMLAudioElement` lifecycle, converts Base64 audio data from OpenAI into Blobs for playback, and broadcasts periodic timing events back to the Service Worker.
- **src/offscreen.html**: A minimal HTML document required by the Chrome Offscreen API to host the `offscreen.js` script in a DOM-enabled environment.
- **tests/**: The central directory for testing configuration and shared utilities.
- **tests/setup.js**: Configures the testing environment, including JSDOM setup and mock implementations for Chrome APIs and other browser globals.
- **src/*.test.js**: Component-specific unit tests (e.g., `background.test.js`, `content.test.js`). These tests use Vitest and JSDOM to verify logic in isolation.
- **dist/**: The production build output directory generated by Vite. This folder contains the bundled, minified, and manifest-transformed code ready to be loaded as an "unpacked extension" in Chrome.
- **manifest.json**: The fundamental configuration file for the extension. It declares the `manifest_version` (3), required `permissions` (contextMenus, offscreen, activeTab, scripting), `host_permissions` for API access, and defines entry points for the background worker and content scripts.
- **vite.config.js**: The build configuration file utilizing `vite-plugin-web-extension`. It manages the transformation of `manifest.json`, handles ES module bundling, and ensures environment variables (like `VITE_OPENAI_API_KEY`) are properly injected.
- **.env**: Local environment file (not committed) containing the `VITE_OPENAI_API_KEY`.
- **.env.example**: A template file illustrating the required environment variables for the project to function.
- **artifacts/**: Contains project-related documentation and generated artifacts such as Product Requirements Documents (PRDs).

## 6. Build Commands
- `npm run build`: Performs a production-ready compilation of the extension, outputting files to the `dist/` directory.
- `npm run dev`: Starts Vite in watch mode. It re-compiles the project automatically upon file changes, facilitating a fast developer feedback loop.

## 7. Test Commands
- `npm run test`: Executes all unit tests in the project using the Vitest runner.
- `npx vitest src/background.test.js`: Specifically runs tests for the background service worker. Use this pattern to execute a single test file.
- `npx vitest run`: Runs all tests once and exits (useful for CI/CD).

## 8. Run Commands
- `npm run dev`: Prepares the development build and monitors for changes.
- **Chrome Installation Steps**:
    1. Open Chrome and navigate to `chrome://extensions/`.
    2. Enable **"Developer mode"** via the toggle in the top right corner.
    3. Click the **"Load unpacked"** button.
    4. Select the `dist/` folder located in the project root.
    5. The extension is now active. Pin it to the toolbar for easier access if desired.

## 9. Code Style Guidelines

### 9.1 Module & Import Rules
- **Import Strategy:** Strictly use ES Modules (`import`/`export`). External dependencies (like `openai`) must be imported at the top of the file. Use relative paths for internal module imports. Avoid using `require` or commonJS patterns as the project is configured with `"type": "module"`.
- **Export Strategy:** Prefer named exports for utility functions to improve tree-shaking and maintainability. Default exports should be used sparingly, primarily if required by a specific framework or tool (though not currently required here).
- **Encapsulation:** The Service Worker is the *only* component authorized to make external network requests (OpenAI API). Content scripts and the offscreen document must communicate via `chrome.runtime.sendMessage` to trigger these actions. This ensures API keys and sensitive logic remain in the background context.

### 9.2 Formatting & Naming
- **Naming Conventions:**
    - Variables & Functions: Use `camelCase` (e.g., `extractTextFromImage`, `isPlaying`).
    - Constants: Use `UPPER_SNAKE_CASE` for message types, action IDs, and configuration defaults (e.g., `TTS_SPEAK`, `PLAY_AUDIO`).
    - File Naming: Use `kebab-case` for multi-word filenames.
- **Indentation & Space:** Use 2-space indentation. Maintain a clean code structure with consistent spacing around operators and after commas. Double quotes are preferred for string literals. Follow standard Prettier-like formatting even if a config file is not explicitly present.
- **Clean Diffing:** Always include trailing commas in multi-line objects and arrays to ensure cleaner and more readable Git diffs.
- **Code Comments:** Use JSDoc-style comments for complex functions to describe parameters and return values, especially when dealing with the Chrome Messaging API's asynchronous nature.

### 9.3 Error Handling
- **Pattern:** All asynchronous operations (especially `fetch`, `chrome.*` APIs, and OpenAI calls) must be wrapped in `try/catch` blocks. For Chrome APIs that use callbacks, always check `chrome.runtime.lastError`.
- **Messaging Safety:** Use `chrome.runtime.lastError` checks when sending messages to ensure the receiving end is active and the message was delivered. Always provide a fallback or user-facing error message if a message fails to reach its destination.
- **Logging:** Use `console.log` for development debugging. Critical failures and API errors should be logged using `console.error` with descriptive context. Avoid excessive logging in production-ready code.
- **Input Validation:** Always trim and validate text inputs before sending them to the translation or TTS APIs to avoid unnecessary token usage or API errors. Verify the existence of `tab.id` before attempting to inject scripts or send tab-specific messages. Ensure that Base64 strings are properly formatted before attempting to decode them in the offscreen document.
- **Resource Management:** Ensure that `URL.revokeObjectURL` is called in the offscreen document once audio playback is finished or stopped to prevent memory leaks. Stop any active intervals or timeouts during cleanup.
